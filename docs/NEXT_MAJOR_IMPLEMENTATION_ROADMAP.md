## 1. 使用方式

本文件回答四个问题：

1. 下一超大版本按什么顺序实现；
2. 每一步必须交付什么；
3. 怎样判断该步骤真正完成；
4. 哪些节点需要产品确认后才能继续。

里程碑状态统一使用：

```text
pending       尚未开始
in-progress   正在开发
verifying     自动测试通过，等待人工/实机验收
accepted      已验收，可以作为后续依赖
blocked       存在明确阻塞，不能继续
```

只有 `accepted` 的里程碑可以成为后续工作的稳定依赖。不能因为“代码已经写完”就直接标记完成。

## 2. 总体顺序

```text
D0 架构记录
  -> R0 当前行为与资源基线
  -> R1 协议和 schema 冻结
  -> R2 Module Manager 与 ResourceRegistry
  -> R3 Capability 权限网关
  -> R4 现有后台模块生命周期接入
  -> R5 前端 Contribution Registry
  -> R6 装配方案运行时与兼容迁移
  -> R7 DIY 装配编辑器 MVP
  -> R8 Profile 导入导出
  -> R9 统一组件运行时
  -> R10 隔离 DLL 宿主与组件包安全
  -> R11 工作流执行器与可视化节点编辑器
  -> R12 参考装配纵向验收
  -> R13 Blender 远程渲染农场
  -> R14 稳定性、升级与正式发布
```

关键依赖原则：

- 没有 R2 生命周期管理，不能开始真正模块开关；
- 没有 R3 权限网关，不能向组件开放文件、网络和渲染能力；
- 没有 R5 贡献注册表，不能做可自由装配的界面；
- 没有 R6 Profile 事务切换，不能做装配编辑器；
- 没有 R9 组件运行时，节点编辑器只能连接内置动作；
- 没有 R11 工作流的幂等、恢复和远程执行模型，不能建设渲染农场；
- R12 必须证明系统能组装出多种形态，才说明 DIY 平台成立。

## 4. 通用完成定义

每个里程碑必须同时满足以下条件：

### 4.1 工程完成

- Rust/TypeScript 类型和公开接口已经确定；
- 数据迁移幂等，可重复执行；
- 错误使用稳定错误码；
- 长任务有进度、取消、失败和恢复状态；
- 新资源已登记到 ResourceRegistry；
- 文档、帮助提示和相关架构记录同步更新；
- 不覆盖或删除不属于本任务的用户修改。

### 4.2 自动验证

最低命令：

```powershell
npm run build
cd src-tauri; cargo test --lib
cd src-tauri; cargo check
git diff --check
```

涉及数据库、网络、文件系统、组件或渲染时，必须增加对应集成测试，不能只依赖编译通过。

### 4.3 人工验证

- 正常桌面宽度；
- 窄窗口；
- 深色和浅色主题；
- 首次启动、重启恢复和异常退出恢复；
- 没有活动项目和有活动项目；
- 成功、失败、取消、阻塞和权限拒绝状态；
- Windows 实际进程、端口、文件句柄和通知行为。

### 4.4 验收证据包

每个里程碑提交验收时必须附带：

- 变更摘要和影响范围；
- 新增/修改的公开接口；
- 自动测试命令和结果；
- 关键页面截图或录屏；
- 数据迁移前后结果；
- 资源释放证据，例如端口、进程、线程和文件句柄；
- 已知限制和残余风险；
- 回滚或关闭新功能的方法；
- 产品确认结论。

### 4.5 产品确认状态

产品验收只使用三种结论：

```text
接受：进入下一里程碑
修改：列出问题，当前里程碑保持 verifying
延期：保留实现但不作为后续稳定依赖
```

## 13. R7：DIY 装配编辑器 MVP

### 目标

用户不编辑 JSON，也能从空白空间组装软件外观和入口。

### MVP 范围

- 添加/移除模块；
- 选择首页和导航页面；
- 添加 Surface、Widget 和详情面板；
- 拖动工具栏入口、页面和响应式网格部件；
- 绑定命令、数据源和已有工作流；
- 属性面板编辑参数和显示条件；
- 实时预览；
- 保存前依赖、权限、路径和布局检查；
- 撤销、重做和版本历史。

### 明确不做

- 不允许任意 React/HTML 注入；
- 不在此阶段制作复杂逻辑节点画布；
- 不允许绕过 Module Manager 直接启动服务。

### 自动验收

- Profile round-trip 不丢布局和绑定；
- 无效部件、重复 ID、缺失命令和循环布局被拒绝；
- 桌面/窄屏布局不会重叠；
- 撤销、重做和保存恢复一致；
- 模块停用后相关部件显示明确缺失状态，不让整个方案损坏。

### 产品实操验收

从空白装配开始，在不修改代码和 JSON 的情况下完成：

1. 一个只有联系人、聊天、传输和设置的通信界面；
2. 一个只有渲染队列、节点状态和任务日志的渲染界面；
3. 保存、关闭、重启并恢复；
4. 复制方案后修改布局，原方案保持不变。

完成以上操作且体验可理解，R7 才能 accepted。

## 16. R10：隔离 DLL 宿主与组件包安全

### 目标

支持高性能 DLL，同时保证 DLL 崩溃不结束 PM Center。

### 实施内容

- `pmc-component-host.exe`；
- 稳定 C ABI 和版本协商；
- 命名管道/本地 RPC；
- DLL 哈希、签名、架构和发布者检查；
- 每组件或每信任组的宿主隔离；
- `.pmc-pack` 安装、更新、回滚和卸载；
- 权限审批和许可证展示。

### 自动验收

- 错误架构、损坏、未签名或 ABI 不兼容 DLL 被拒绝；
- DLL 主动崩溃时 PM Center 保持运行；
- 宿主重启后不会重复提交结果；
- 卸载不会删除组件用户数据，除非明确选择；
- 包路径穿越、压缩炸弹和恶意文件名被拒绝。

### 人工验收

运行一个测试 DLL，分别触发正常完成、异常返回、死循环、内存增长和进程崩溃，确认诊断与恢复符合预期。

## 17. R11：工作流执行器与可视化节点编辑器

### 目标

让用户像连接 Blender 节点一样组合触发、条件、动作、组件、人工确认和结果提交。

### 固定实现顺序

#### R11-A：无界面 DAG 执行器

- Workflow Manifest；
- 拓扑排序、分支、并行、等待和有限循环；
- 节点输入输出 schema；
- operationId、claimToken 和幂等提交；
- 取消、重试、超时、补偿和崩溃恢复；
- 本地/远程执行位置抽象。

#### R11-B：节点类型

- Trigger：按钮、快捷键、文件变化、定时、消息、任务事件；
- Data：项目文件、媒体项、联系人、变量、渲染批次；
- Condition：类型、状态、路径、在线和数值判断；
- Action：复制、解析、传输、渲染、通知和组件动作；
- Interaction：确认、参数表单和文件选择；
- Flow：分支、合并、并行、等待、重试和超时；
- Output：数据库提交、归档、渲染结果和页面反馈；
- Remote：选择设备、发送任务、等待节点和回收结果。

#### R11-C：可视化节点编辑器

- 使用成熟节点画布库，优先评估 `@xyflow/react`，不手写缩放、连线和选择引擎；
- 节点搜索、拖入、端口类型、连线检查和自动布局；
- 右侧属性面板；
- 小地图、缩放、框选、多选、复制和分组；
- 节点运行状态、断点、单步测试和数据预览；
- 工作流版本历史和差异；
- 只读模块依赖图与可编辑逻辑图分离。

### 自动验收

- 有环 DAG、类型不兼容端口和缺失节点被拒绝；
- 并行节点不会重复提交；
- 崩溃恢复不会重新执行已提交的不可重复动作；
- 取消传播到本地组件和远程节点；
- 1000 节点测试图仍可加载、保存和校验；
- 节点编辑器保存结果与无界面执行器完全一致。

### 产品实操验收

不用写代码完成并运行：

```text
选择目录
  -> 查找图片
  -> 检测重复项
  -> 用户确认
  -> 移动到归档目录
  -> 写入备注
  -> Windows 通知
```

同时完成一个“接收局域网文件后自动归档”和一个“创建渲染批次后装配并发送”的流程草案。

### 目标

不新增固定模式分支，只使用装配编辑器、模块、组件和工作流验证平台能形成完全不同的软件形态。

### R12-A：当前项目管理器装配

- 现有功能、会话和数据兼容；
- 可以关闭局域网、渲染或剪贴板；
- 停用后真实释放资源。

### R12-B：媒体资料管理器装配

- 建立媒体库；
- 引用/复制/移动收集；

- 图片、视频和序列帧预览；

### R12-C：局域网通信端装配

- 不打开项目即可使用；
- 不初始化项目 watcher、项目数据库和渲染；
- 联系人、聊天、文件/目录传输、通知和托盘可用；

### 总体验收

四个参考成品全部通过同一 Profile schema 和 Contribution Registry 形成，代码中不存在按这四个 Profile ID 写死的分支。

## 19. R13：Blender 远程渲染农场

### 目标

在已经验收的节点引擎、组件运行时和局域网同步上实现控制端与渲染节点协同。

### 实施顺序

1. 设备身份、配对、撤销信任和加密通道；
2. 节点 CPU/GPU/内存/磁盘/Blender/插件能力报告；
3. `.pmc-renderpack` 和资源 manifest；
4. 内容哈希比较、分块同步和断点恢复；
5. 远程任务租约、claimToken 和帧领取；
6. 节点 staging、渲染、校验和结果上传；
7. 控制端原子提交、ETA、性能和失败恢复；
8. 多节点公平调度、限流和节点下线恢复。

### 自动验收

- 不可信设备不能领取任务；
- 缺 Blender、插件、贴图或磁盘时预检阻止；
- 多节点不重复领取或覆盖帧；
- 断线、崩溃和重启后任务租约正确恢复；
- 源 `.blend` 变化进入 attention；
- 旧节点结果不能覆盖新结果；
- 禁止任意脚本、shell 和越界路径写入。

### 双机实景验收

- 两台 Windows 设备配对；
- 使用真实 `.blend` 和至少 10 帧任务；
- 验证每个节点资源同步、渲染和回传；
- 控制端最终帧完整、无重复、无混合版本；
- 中途断网、暂停、节点崩溃和控制端重启各测试一次；
- 源文件和最终输出哈希记录完整。

## 22. 变更控制

出现以下情况时必须先更新架构文档和路线图，再继续编码：

- 新增一种组件运行时；
- 新增高风险 Capability；
- 改变 Profile、Workflow 或包格式；
- 允许组件执行远程命令；
- 改变模块停用时的数据处理；
- 改变媒体资料库或渲染任务的数据所有权；
- 绕过 ResourceRegistry 创建长期线程、端口或进程；
- 为某个参考装配增加写死的系统分支。

本路线图是顺序和验收约束，不是固定时间表。具体版本号、周期和人员安排在里程碑进入 `in-progress` 前单独确定。
