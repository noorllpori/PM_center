# 架构自洽与扩展性审计

状态：当前代码与文档交叉检查，2026-08-07。此审计区分已经可用的能力、明确限制与应在后续版本补强的架构债务。

## 1. 结论

Nexora 的核心方向是自洽的：**Profile 选择功能闭包，Module 管理产品生命周期，Component 提供可安装能力，Capability 约束宿主接口，Contribution 决定可见入口，ResourceRegistry/运行时负责停止与恢复。** 这足以支持“项目管理器、媒体资料库、局域网通信端、外部 Blender 渲染器”等不同装配，而无需把它们固化为互斥产品模式。

后续扩展的主要难点不在于再增加运行时类型，而在于把“已经可表达的字段”严格分成“可由第三方稳定使用”和“暂时只供本体目录/诊断使用”。在这条边界未收紧前，贸然建设商城或鼓励第三方任意 UI 注入，会带来兼容性与安全债务。

## 2. 已自洽的部分

| 范围 | 当前保证 | 证据入口 |
| --- | --- | --- |
| 装配切换 | Profile 先预检，切换中有 journal/回滚；模块停用不删除用户数据。 | `profile_runtime.rs`、R6/R7 文档与测试。 |
| 资源释放 | 项目关闭释放 watcher、数据库和 TreeCache；组件与渲染操作有取消、超时、进程树清理。 | `project_resources`、`component_runtime.rs`、`render_center`。 |
| 包安全 | `.pmc-pack`/`.pmc-workspace` 具有清单、摘要、路径限制、staging 和原子提交；可执行组件需要可信发布者。 | `component_runtime.rs`、`profile_package.rs`、R10 文档。 |
| 权限 | 调用能力组件必须消费与主体、操作和范围匹配的一次性令牌。 | `capability_gateway.rs`、`platform/mod.rs`。 |
| 自动化恢复 | 每次运行保留快照；幂等与非幂等恢复语义不同，避免未知结果被静默重放。 | `script_automation.rs`、R11 文档。 |
| 文件路由 | 文件打开先路由，处理器缺失时普通打开回落系统程序，严格检查不伪装成功。 | `file_router.rs`、R10 文档。 |

## 3. 已知边界，不应被误解为缺陷

1. **媒体资料库不依赖项目资源。** 这使它可在无项目装配中使用。项目级媒体关联是后续可选桥接组件，不应让基础资料库常驻项目 watcher。
2. **主页不是唯一入口。** 独立 Shell 页面可以同时作为启动主页、导航项和快捷栏工具；三者都聚焦同一单例标签。
3. **组件不是 OS 沙箱。** 签名与信任决定是否允许代码运行；Capability 限制 Nexora 提供的接口，但不能阻止受信任 Python/EXE 使用当前用户权限。
4. **装配空间不是项目归档。** `.pmc-workspace` 只交付方案、变量、页面骨架和可重分发组件包，不携带项目文件、聊天、私钥或绝对路径。
5. **R13 不是已可用农场。** 已完成可信身份、租约和加密信封控制面；真实网络传输、远程 Worker、资源续传和双机渲染仍未实现。

## 4. 扩展 API 成熟度

| 能力 | 目前可作为第三方稳定入口 | 说明 |
| --- | --- | --- |
| 组件 Manifest、依赖、版本、签名包 | 是 | v1 Schema 是合同来源。 |
| Python 自动化命令与 `nexora_sdk` | 是 | 适合大部分业务扩展；使用脚本 Surface 提供受控 UI。 |
| EXE、Python Worker、DLL、资料包运行时 | 是，但需协议/平台测试 | DLL 仅 Windows 且隔离；优先 Python 或 EXE。 |
| 文件处理器与用户文件关联 | 是 | 通过 `fileHandlers` 和文件路由，不直接拦截前端双击。 |
| Schema 设置区、模板与主题 | 是 | 设置字段由宿主渲染；模板经静态净化和恢复容器托管。 |
| Script Surface 的任意位置自动嵌入 | 尚未实现 | 当前从功能中心打开为对话框；`placements` 不会自动生成 Shell、工作区或 Widget 宿主。 |
| 任意 React/DOM 注入、任意 Tauri command | 否 | 不公开，禁止依赖。Script Surface 运行在沙箱 iframe。 |
| 任意宿主菜单、Widget、DataSource 的自定义渲染器 | 尚未形成独立第三方 UI ABI | Manifest 字段可被记录/诊断，但没有开放直接加载第三方 React 的宿主 ABI。新 UI 应优先走 `scriptSurfaces`。 |
| 节点 DAG 执行器 | 否 | `workflowNodes` 是冻结兼容合同，R11 不执行节点图。 |
| Marketplace/云端账户 | 规划 | 当前包、签名和依赖锁可作为基础，但服务端协议尚未定义。 |

## 5. 主要架构债务与建议

### P0：把“公开 API”做成单一事实来源

当前 Schema、Rust 语义、前端目录、示例和历史里程碑文档并存。已有平台合同检查，但第三方难以判断字段是否真的拥有宿主实现。

建议：将 `docs/extension-development/INTERFACE_REFERENCE.md` 作为发布入口；每次发布从 Schema 和 SDK 生成版本目录、能力矩阵与兼容性清单，并在 CI 检查示例包可安装、可调用、可卸载。

### P0：明确 UI 贡献分级

Component Manifest 已能表达多种贡献，但宿主并未开放任意 React 代码加载。若文档不说明，开发者会误以为声明 `widgets` 就能获得原生 Widget。

建议：保持 Script Surface 为第三方 UI 的唯一公开路径；未来若开放 Widget/菜单，先设计独立 `hosted-ui.v1` 结构化协议和性能/权限模型，再宣布稳定。

### P1：减少双份贡献目录的漂移风险

内置 Module Manifest 与前端 `contributionRegistry.ts` 分别声明同一贡献。当前诊断能发现运行时不匹配，但仍属于运行后检查。

建议：在 CI 增加静态清单快照或从一处生成另一处；至少让 `check:platform-contracts` 同时校验 Module、前端贡献、渲染器、工具打开目标和示例 Profile。

### P1：把开发模式从“可用”收束为可复现流程

应用内已经能创建模板、信任目录、热重载、调试和签名，但缺少专门的公开开发者路线与兼容矩阵。

本次新增的扩展开发文档先补齐流程。后续应增加稳定脚手架版本、包 lint、示例测试命令和干净用户环境验收模板。

### P2：发布前关闭真实环境空白

R12/R13/R14 仍缺 MSI 升级/回滚、第二台设备、真实 Blender、真实素材压力和农场传输。它们是发布阻断项，而不是文档问题。

## 6. 推荐的扩展开发难度梯度

1. **资料包或主题模板**：最低风险，不执行第三方代码。
2. **Python action + Script Surface**：推荐默认方案，适合绝大多数解析、批处理、项目规则和小型工具。
3. **Python Worker / Native Process**：适合长驻服务、重计算和现有 CLI 复用，需要处理行协议、取消和资源限制。
4. **Native Library**：仅在性能和 ABI 投入合理时使用，必须接受 Windows/架构/隔离宿主约束。
5. **远程节点或云服务**：在 R13 实际传输和未来商城/账户协议稳定前，不应作为第三方公开承诺。

## 7. 后续维护检查表

- 新增组件字段：Schema、Rust 语义、前端类型、示例、文档和包导入检查同步提交；
- 新增用户入口：说明其 Module/Component 所有权、Profile 引用、停用和卸载后的行为；
- 新增后台资源：ResourceRegistry、取消、超时、退出、切换和异常恢复都有测试；
- 新增 UI 扩展能力：先定义隔离、消息、性能、权限和恢复协议，禁止直接暴露宿主 DOM；
- 任何“可分发”主张：至少经过干净用户、缺依赖、签名不信任、升级、卸载和回滚验收。
